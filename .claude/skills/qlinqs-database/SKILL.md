# Qlinqs core-api database

The real shape of the `qlinqs_core_api` Postgres database and the Eloquent
layer on top of it, verified against the running app (not the conceptual
product docs). Read the linked reference files for full detail; this page is
the map.

For the HTTP API built on this database (routes, request/response shapes,
Scramble discrepancies), see `core-app/docs/API-MAPPING.md` — don't duplicate
it here, link to it when a route matters.

## How it works

- **Postgres runs in Docker Compose**, not on the host. Containers:
  `qlinqs-core-api-app` (Laravel, `docker-php-entrypoint … php artisan serve
  --host=0.0.0.0 --port=8000 --no-reload`, published on host `:8000`) and
  `qlinqs-core-api-db` (`postgres:17-alpine`). Compose project name:
  `qlinqs-core-api`.
- **Ports:** inside the Docker network the app reaches Postgres at
  `db:5432` (set via `docker-compose.yml`'s `environment:` block, overriding
  `.env`). From the host, Postgres is published on **`5433`**, not 5432 —
  the host already runs its own Postgres on 5432 (Homebrew), and this
  project must never touch that one. `.env`'s `DB_HOST=127.0.0.1` /
  `DB_PORT=5433` is for host-side tools (e.g. a host `php artisan tinker`
  outside the container); the container's own env vars win when you run
  `docker compose exec app …`.
  DB name `qlinqs_core_api`, user/password `qlinqs`/`qlinqs`.
- **`citext` extension** is enabled (`profiles.slug` uses it) so slug
  lookups and uniqueness are case-insensitive at the DB level — `teste` and
  `TESTE` collide. Don't add app-side `Str::lower()` to fight this.
- **Key types are deliberately mixed:** every identity/content table
  (`users`, `profiles`, `pages`, `templates`, `assets`) uses a `uuid` PK via
  Laravel's `HasUuids` (generated app-side, no DB default). The two
  high-volume, insert-only analytics tables (`page_views`, `block_clicks`)
  use a plain **bigint identity** PK (`GENERATED BY DEFAULT AS IDENTITY`) —
  cheaper and there's no cross-service need for those rows to have globally
  unique IDs.
- **Relational vs JSONB split:** relational tables hold identity, routing,
  file metadata, and analytics — data with fixed shape that needs FKs,
  uniqueness, or aggregation. `pages.content` and `pages.theme` (and
  `templates.theme`) are JSONB — polymorphic, nested, and meant to grow
  without a migration. Postgres only guarantees "valid JSON" for those two
  columns; **the app (`app/Validation/*`) is the only source of truth for
  their actual shape** — see `reference/jsonb-shapes.md`.

## Tables

Full column-by-column detail (types, nullability, defaults, PK/unique/index,
FK + `ON DELETE`) is in **`reference/schema.md`**. At a glance:

| Table | PK | Purpose |
|---|---|---|
| `users` | uuid | Sanctum-style local auth table. Stands in for the conceptual doc's `auth_users`. No login/registration flow exists yet. |
| `profiles` | uuid | Identity + routing (`slug`, citext, unique). One profile per user (`user_id` unique). |
| `pages` | uuid | One page per profile (`profile_id` unique). `content`/`theme` JSONB. |
| `templates` | uuid | Curated starter themes (`theme` JSONB). No relationship to `pages` — applying one is a copy. |
| `assets` | uuid | Upload metadata, owned by `profile_id` (not `page_id`), for future cross-page reuse. No upload endpoint exists yet. |
| `page_views` | bigint identity | One row per page view. No tracking endpoint exists yet. |
| `block_clicks` | bigint identity | One row per block click. `block_id` is a logical reference into `pages.content`'s JSONB — no FK. |

**Quirks worth knowing before you touch any of these:**
- `users.created_at`/`updated_at`/`email_verified_at` are plain
  `timestamp` (no timezone) — the Laravel-default `$table->timestamps()`
  macro. Every other table explicitly uses `timestamptz`. This is an
  inherited framework-skeleton inconsistency, not a bug.
- `profiles.user_id`'s FK has **no `ON DELETE` clause** — deleting a user
  with a profile is blocked by Postgres (RESTRICT), not cascaded.
- `templates` and `assets` have **no `updated_at` column at all** — not
  unused, the column doesn't exist. Both models set `const UPDATED_AT =
  null`.
- `page_views`/`block_clicks` have **no `created_at`/`updated_at`** either;
  their one timestamp (`viewed_at`/`clicked_at`) is a DB-side
  `CURRENT_TIMESTAMP` default, not managed by Eloquent — both models set
  `public $timestamps = false`.
- `pages.content`'s DB default is a bare `'{}'::jsonb` — no `header`,
  `socialIcons`, or `blocks` keys. That default alone does **not** satisfy
  `PageContentRules` (see below). Every page in the running system today is
  created via `PageFactory`/the seeder, which always produces a valid
  shape, so this is latent, not currently hit — but don't rely on the raw
  DB default if you ever insert a page row outside the factory/seeder.

## The Eloquent layer

Per-model detail (key type, casts, timestamps behaviour, relationships in
both directions, factories) is in **`reference/models.md`**. Summary:

`User` → `hasOne Profile`. `Profile` → `belongsTo User`, `hasOne Page`,
`hasMany Asset`. `Page` → `belongsTo Profile`, `hasMany PageView`, `hasMany
BlockClick`; casts `content`/`theme` to `array`. `Template` → no
relationships, by design. `Asset`/`PageView`/`BlockClick` → `belongsTo`
their parent only. A factory exists for every model and always produces
data that passes the JSONB validators (`PageFactory`/`TemplateFactory`
share `PageFactory::defaultTheme()`).

## The JSONB shapes (`pages.content`, `pages.theme`, `templates.theme`)

Enforced by `app/Validation/PageContentRules.php`,
`PageThemeRules.php`, and the shared `StyleOverrideRules.php` — wrapped by
`ValidatePageContentRequest`/`ValidatePageThemeRequest`. Full field-by-field
rules (required/present/nullable, enums, ranges, `prohibited`) and one
minimal valid example of each are in **`reference/jsonb-shapes.md`**.
Headline points:

- `content` is always `{ header, socialIcons, blocks }`. Blocks are either
  **atomic** (`type`: `link`/`whatsapp`/`maps`/`text`/`heading`, one
  `card`) or **container** (`type`: `carousel`/`grid`, a `config` object
  and an `items` array of cards — containers never contain containers).
  The `link` type has 4 layouts: `button`/`thumbnail`/`background`/
  `featured` — `background` is a Qlinqs addition (image fills the button,
  title overlaid), not in the conceptual data doc.
- `theme` is always `{ page, blockDefaults, fonts, palette }`. Style
  overrides (`tactile`, `color`, `corner`, …) are shared between a block's
  `card.overrides` and `theme.blockDefaults`, except `align`/`size`/
  `imagePosition`, which are **block-only** — allowed in `card.overrides`
  (and container item `overrides`), **`prohibited`** (422) in
  `blockDefaults`. `imagePosition` (`left`/`right`) is also a Qlinqs
  addition (link `thumbnail` layout's image side), not in the conceptual
  doc.
- Persistence: `PageController` saves `Arr::only($request->all(),
  $topLevelKeys)`, **not** `$request->validated()` — nested fields the
  validator doesn't explicitly enumerate are kept as sent; only unknown
  **top-level** keys get dropped. Don't "simplify" this to `validated()`;
  that regressed a real bug once (see `core-app/docs/API-MAPPING.md` §2).

## Commands

```sh
colima start                 # if the Docker daemon is unreachable
docker compose up -d         # bring Postgres + the app up

# Migrations (always inside the container — never on the host)
docker compose exec app php artisan migrate
docker compose exec app php artisan migrate:status
docker compose exec app php artisan migrate:rollback --step=11   # 11 = all migrations today
docker compose exec app php artisan db:table pages   # quick schema + FK summary for one table

# psql, direct
docker compose exec db psql -U qlinqs -d qlinqs_core_api
#   \d <table>                      -- full column/index/FK detail
#   \dx                             -- confirm citext is installed
#   select content, theme from pages where id = '...';
#   select jsonb_pretty(content) from pages where id = '...';   -- inspect one page's JSONB readably

# Pest — runs on the HOST against a real Postgres test database
# (qlinqs_core_api_test, same container, see phpunit.xml), not SQLite —
# citext/jsonb don't exist there. Needs the db container running.
./vendor/bin/pest
```

## Gotchas for whoever edits this next

- **Run migrations inside the `app` container**, not on the host — the
  host's PHP has no reason to see this database directly, and running
  artisan on the host uses `.env`'s `127.0.0.1:5433`, which only works if
  the container's port mapping is up anyway.
- **Never point anything at host port 5432** — that's a separate Homebrew
  Postgres unrelated to this project. This project's Postgres is always
  `5433` from the host, `db:5432` from inside the container.
- **Never add `align`, `size`, or `imagePosition` to `theme.blockDefaults`**
  — they're block-only by design and the validator will 422 on them.
- **Templates are copied, not linked.** Applying a template
  (`POST /api/page/apply-template/{template}`) copies `theme` into
  `pages.theme`; there is no FK and no Eloquent relationship between
  `templates` and `pages`. Editing or deleting a template must never affect
  a page that already applied it — don't add that FK "for integrity."
- **`ON DELETE CASCADE` on `assets` only removes the DB row**, not the
  object in the storage bucket. Deleting the physical file is the
  application's job (and there's no upload/delete endpoint yet to do it).
- **`profiles.user_id` has no cascade** — deleting a user with an existing
  profile fails at the DB level today. If a "delete account" flow is ever
  built, decide the cascade behavior deliberately rather than assuming one.
